# Simulation architecture

## World contract

Current offline integration adds `OfflineMatchState`, `FogOfWarSystem`, `OfflineAiObservation` and `OfflineAi` to the existing Unity-free world. `OfflineMatchDefinition.Enabled` explicitly opts a map into a two-participant match; legacy maps have no match/fog state. The [Phase 7 report](../tasks/PHASE_7_REPORT.md) describes validated rule boundaries; the [Phase 10 report](../tasks/PHASE_10_REPORT.md) records measurements and accepted optimization. All checkpoint counts below are historical.

Phases 11–13 also run this World in a dedicated C# authority. Online clients apply recipient-specific `NetworkSnapshot` observations to read-only replicas: their `World.Tick` does not advance simulation, and `World.Submit` forwards through a bounded command sink. The authority validates account-bound ownership and visibility before ordinary rule validation. See [multiplayer architecture](MULTIPLAYER_ARCHITECTURE.md) and [current verification](../tasks/CURRENT_PHASE.md) for the live contract and final test totals.

The controller submits ordinary opponent AI commands, then calls `World.Tick`. Tick order is: vision refresh; faction bonuses; movement; vision/bonuses; economy; construction; vision; combat; faction actions; production; research; bonuses/vision; tick index increment; victory/objective evaluation. Accepted commands that create or transform vision sources refresh visibility at their boundary. Finished matches reject further gameplay commands and freeze ticks.

Each participant has separate current-visible and explored cell masks. Own entities remain observable; enemy units use their centre and buildings their footprint. Vision is a disc over map cells, with no terrain occlusion. Explicit target commands and new attack acquisition require current visibility; losing sight stops target tracking. Already-launched projectiles retain their existing attack contract. Full placement footprints require current vision.

The strategic AI uses a visibility-filtered observation with last-seen records, its own economy and public terrain/objectives. Its bounded cadence and normal command spending remain independent of rendering. Simulation owns capture, continuous-majority clocks, elimination, surrender and draws; presentation owns pause/menu, touch input, minimap, camera and cosmetic effects. The debug HUD must not disclose hidden-state entity counts.

The foundation is a plain C# assembly with `noEngineReferences`, explicit world ownership and a **20 Hz** fixed tick. Entity IDs are stable within a world. Definitions use stable content IDs. Integer millimetres represent authoritative planar positions; one Unity metre is 1,000 simulation millimetres. Map bounds and permitted speeds must be validated before world creation. Unity transforms are outputs, never gameplay authority.

The command API applies validated order changes synchronously between ticks on the world's owning thread; it does not yet provide a scheduled network command queue. The current order is **Movement → Economy → Construction → Combat → Faction actions → Production → Research → increment TickIndex**. Faction influence and effective carry/speed refresh before movement, after movement, after faction timers/transitions and after research. Consequently, harvesting uses coverage at the worker's new position; combat destruction wins over charter completion and pack/deploy conversion; newly completed Muster influence can help production that tick. Research still updates attack/armor/gather caches after combat and harvesting, with upgraded actions beginning on the following tick. A unit produced on the completion tick is included in that completion's stat update. Newly produced units first move or attack on the following tick; newly packed transports first move on that tick. Future systems should declare ordering and observable events rather than each adding a `MonoBehaviour.Update`. A later replay/network scheduler must define command ordering and tick assignment explicitly.

The presentation driver accumulates elapsed frame time, advances fixed ticks and renders state. It clamps each frame's elapsed time to 250 ms and advances at most five ticks per frame; focus loss clears accumulated time. This keeps local catch-up bounded but sacrifices wall-clock progression during long stalls. The Phase 4 player probe records simulated seconds divided by wall seconds and requires a ratio from 0.95 through 1.05. That aggregate diagnostic does not change the driver or provide an authoritative network clock policy.

## Commands and state

The command boundary must validate ownership, entity existence, supported actions and coordinate bounds. Invalid commands leave authoritative gameplay state unchanged and produce a reason usable by tests and local feedback; navigation caches and diagnostic counters may still change while validating a rejected order. Selection is local presentation state; submitting an order converts selected IDs into a command. Display objects cannot bypass validation.

Do not use wall-clock time, rendering state or device input inside rule systems. Balance values enter through validated configuration. Entity removal and system iteration must have clear ordering; external consumers should receive read-only views or snapshots wherever practical.

Future replay envelopes should contain simulation version, content hash, map ID/seed, issuer, monotonically ordered command sequence and target tick. None of these fields alone makes local execution authoritative or secure.

## Phase 4 movement contract

Move/Stop selections are sorted by stable entity ID, reject duplicates and foreign/missing units, and contain at most 1,024 units. Move computes all legal destinations and routes before cancelling prior tasks. Idle bodies and other groups' destination reservations constrain slot choice; a blocked static target rejects, while an idle unit occupying a walkable click can resolve to a nearby slot. Formation spacing leaves passage space for late arrivals. Repeated intact-group orders preserve assigned goals, while Stop, worker reassignment and automatic combat clear obsolete group identity.

`MoveCommand` accepts an optional fourth argument, `MovementFormation`, defaulting to Loose. `FormationPlanner` separates destination allocation from pathfinding. Loose retains offsets and expands only if nearest-pair spacing needs more clearance, avoiding repeated fixed-scale growth; Line makes one lateral row and Box makes a roughly square grid, both oriented by the dominant cardinal travel axis. Obstructed preferred layouts fall back to free slots. Accepted `UnitState.Formation` records the requested mode; changing mode replans, while repeating the same target/mode preserves the group. Invalid formation values reject atomically.

The tick indexes body bounds in a reusable uniform grid and processes units from a deterministically rotating start index. Every accepted step checks the swept circle against static footprints and relative-motion sweeps of neighbouring units. Initial overlap rejects world creation; idle bodies are not displaced by passing units. Integer speed accumulation and explicit rounding bounds keep movement independent of rendered frame rate. Geometry uses wide integer products with a decimal overflow fallback. Cross-runtime replay equality still requires verification.

Groups of at least four reuse static distance fields; each navigation instance retains at most four anchor-cell fields and clears them when connectivity changes. Per-unit paths and local recovery retain their own final goals. Recovery searches are limited to four per tick, a fixed 25 by 25 sample lattice at half-cell spacing and a 20-tick cooldown per unit. Chosen straight segments are reused; new segment selection performs at most 12 visibility checks, while each immediate step still checks collision. These limits cover local work, not all global pathfinding, combat pursuit or synchronous construction replanning. See [pathfinding architecture](PATHFINDING_ARCHITECTURE.md) for exact current contracts.

The separate `Emberfield.Diagnostics` assembly also has `noEngineReferences`. Its versioned fixtures and observers read authoritative state without controlling decisions. Opt-in navigation timers never influence movement. The CPU runner measures only the `World.Tick` time/allocation window. The verified replacement packaged probe includes presentation, its 10 Hz observer, forced canvas updates, an explicit URP render request and synchronous one-pixel GPU readback per loop. It measures conservatively serialized offscreen throughput; ordinary displayed gameplay FPS and mobile performance remain unmeasured. The first hidden automatic-camera probe correctly rejected zero rendered frames; its timings are excluded from rendering claims. Measurements identify build `c025db1be65c48f1bbfcb08ef47692eb`; subsequent distribution changes only fit the non-stress Formation label and correct comments, preserving the measured simulation/stress/render path. Arrival, swept safety and rendered throughput are separate acceptance checks; a zero immobility-stall count does not prove that circling units are reaching goals. See [movement stress methodology](../testing/MOVEMENT_STRESS.md).

The HUD's route-search timing covers path/attack queries, local recovery and connectivity work. Ordinary per-step clearance, spatial-neighbour checks, steering and segment-visibility work are included in total `World.Tick` time, not separately in the route-search timer. Checks performed inside an instrumented recovery query naturally remain part of that query's cost. Do not interpret route-search time as the complete navigation/movement budget.

## Numerical discipline

Integer coordinates reduce floating-point drift at the boundary but **do not prove deterministic execution**. Integer square-root/normalization policy, rounding, overflow, collection traversal order, random number generation and platform/runtime differences still matter. Promote intermediate products to a sufficiently wide type, validate ranges and reject impossible data instead of silently wrapping.

Before any deterministic networking claim, add replay hashing and repeated identical-command runs across supported runtimes/devices. Document every source of nondeterminism and define save/snapshot compatibility. The initial greybox should be described as an integer-based prototype, not a verified lockstep engine.

## Economy policies inherited from Phase 2

The presentation's placement preview and contextual buttons submit commands; they do not charge resources or create authoritative entities. `World` composes movement, economy, construction, combat, faction, production and research systems. Player inventories expose Food/Wood/Metal/Stone values, population used, queued reservations and capacity.

Harvesting transfers finite node stock into worker cargo. Only arrival at a reachable, completed, owned drop-off credits spendable inventory. Full cargo and a depleted source trigger a return trip. Depleted sources remain addressable by ID, but their navigation cells are cleared and connectivity rebuilt; hiding their exhausted visuals therefore does not leave invisible resource obstacles.

Move, stop, build and construct orders cancel prior worker assignments while preserving cargo amount and kind. Repeating the same gather assignment is idempotent. Reassigning to a different resource kind first delivers existing cargo before harvesting the new kind. If an inventory approaches `int.MaxValue`, deposit credits only available capacity and preserves remaining cargo. Missing approaches/drop-offs and partially credited cargo retry on a bounded 20-tick interval. Workers with no remaining stock or cargo finish idle.

`ReturnCargoCommand(playerId, workerIds, dropOffBuildingId = 0)` manually delivers preserved cargo, including a stopped final load after every resource node is exhausted. Zero chooses each carrier's nearest reachable completed owned drop-off; an explicit ID must identify a completed owned drop-off reachable by every selected carrier. Validation completes for all carriers before any assignment changes. Selected empty workers retain their existing orders. Carriers cancel their prior gathering/construction assignment, travel physically to the drop-off, credit inventory on arrival and finish idle; manual delivery does not resume their previous gather target. The HUD's Deliver action and tapping a completed own drop-off route through this command.

Accepted foundations spend resources once and block their footprint immediately. Construction updates navigation connectivity and replans moving routes. A failed movement replan keeps its intended destination, clears the route and retries after 20 ticks; active economy/construction tasks also retain bounded approach retries. Initial map buildings are complete. Newly placed buildings grant housing capacity, drop-off eligibility and production only after completion.

Phase 4 interaction permits a worker to halt and act in a valid adjacent footprint cell when its center is within half a cell of the footprint. It need not reach one exact approach-center coordinate. Approach search excludes centers intersecting another idle unit, allowing a replacement builder to use a free side. Cargo still credits only beside an eligible drop-off. Building destruction halts workers targeting that building; carriers seek another drop-off while construction assignments clear.

Training validates the producer, unit, queue limit, resources and population. Accepted queue entries charge costs and reserve population immediately. FIFO production advances only the front entry. A blocked adjacent spawn waits with its cost and reservation intact, then creates the unit when a valid exit becomes available. Spawn checks include units' swept bodies. Each spawned rally order uses the movement slot resolver so later arrivals can settle beside an occupied rally point. If no rally route is available, the unit remains at its valid spawn; production is already complete. Producer destruction cancels that building's queued units and releases their reservations without refunds. Player-requested queue cancellation/refunds remain future work.

The preview currently revalidates through the authoritative placement API at the HUD refresh cadence. Navigation copying and approach searches are candidates for measured allocation/time analysis if visible preview interaction stalls. Do not infer a mobile performance result or add caching without verifying invalidation when resources, selection, workers or obstacles change.

## Combat policies inherited from Phase 3

Unit definitions add armor, composable combat tags and an `AttackDefinition`: damage, edge-to-edge range in millimetres, acquisition range, cooldown ticks, projectile speed, projectile lifetime and tagged damage multipliers. Buildings expose armor and tags but do not attack in this phase. The flags are Worker=1, Infantry=2, Cavalry=4, Ranged=8, Light=16, Heavy=32 and Structure=64. Shipped Stringwardens use Ranged|Light; Infantry identifies the current melee infantry target of their bonus.

A bonus matches if any of its target flags overlaps the target's flags. Choose the highest matching multiplier, with 1000 permille as the no-match default; entries do not stack. Phase 5 damage is `max(1, floor(effectiveAttackDamage * multiplier / 1000) - targetArmor)`, clamped to the supported integer range. Effective attack damage includes the attacker's completed technology additions; unit target armor includes that player's completed armor additions. Building armor remains its definition value. An effective `AttackDamage` of zero is unarmed and does not produce minimum-one hits. A matching attack upgrade can therefore arm a unit whose base damage is zero. Configuration validation bounds arithmetic inputs and rejects invalid tag masks, nonpositive cooldowns/lifetimes and invalid bonus entries.

`AttackCommand` validates every selected living, owned, armed unit and a living enemy unit/building before changing any order. Each attacker must already be in range or have a reachable firing position. Repeated orders preserve cooldown and chase progress. Range includes unit radii or the target building's rectangular footprint. The current ranged model has **no line-of-sight or projectile terrain occlusion**: a target within range may be hit across intervening terrain.

Idle armed units seek the nearest reachable enemy inside acquisition range, with stable entity ID breaking equal-distance ties. Automatic acquisition retries every **10 ticks** (0.5 seconds); chase routes refresh at most once every **5 ticks** (0.25 seconds). An automatic target is released when it leaves acquisition range; an explicit attack may pursue beyond that radius. Stop cancels attacks and holds fire. Explicit move and worker orders cancel combat, then permit automatic acquisition after their own movement/work finishes. Attack cancels a worker assignment while preserving carried cargo.

Combat first reduces cooldowns and resolves already flying projectiles. All actors still alive after those projectile impacts then make attack decisions. Melee damage is staged until those decisions finish, allowing simultaneous lethal melee attacks to kill both actors rather than granting the first entity ID an exclusive strike. Staged hits resolve in stable order with fresh target lookups, preventing repeated death bookkeeping. A projectile that kills an actor before decisions legitimately prevents that actor's later attack.

Projectiles snapshot final damage on release, home toward their target using integer movement, and survive their source's death. A dead target causes a miss/removal. Default lifetime is **400 ticks** (20 simulation seconds), configurable from 1 to 36,000 ticks. Each advance after launch consumes one lifetime tick; a still-airborne projectile expires at zero without damage. The lifetime bounds pursuit of a target that outruns the projectile. Presentation reads projectile positions and lifetime state; collision and damage remain in simulation.

Death removes an entity from active lists and ID lookups once; dead IDs are never reused. Outpost relocation is a living entity's explicit building/unit transformation under its existing ID, not death or ID recycling. Unit death releases used population and loses carried cargo without crediting inventory. Building death releases its queued population reservations without refunding costs, removes completed housing capacity, clears its blocked footprint and replans routes. Capacity may fall below current population: existing units survive, while new training/spawning waits for legal capacity. Returning workers seek another eligible drop-off; construction assignments targeting a destroyed site end. Construction adds only newly earned progress health, preserving earlier combat damage through completion. These are prototype death rules, not conquest/victory logic.

## Phase 5 era and research contract

`GameDefinition.Eras` and `Technologies` are plain serializable arrays. Empty or null arrays preserve legacy fixtures: without configured eras, a player has `EraId = null` and `EraTier = 1`. Technologies without era references can also operate without an era catalog. When eras are configured, validation requires exactly four unique tiers, numbered 1 through 4, and one advancement technology for each transition to tiers 2, 3 and 4. Every player begins at tier 1; maps do not override the starting era.

`TechnologyCatalog` validates IDs, producer references, prerequisite references, costs, durations, effect kinds/tag masks/positive amounts and cumulative matching stat totals. A technology prerequisite graph cannot contain cycles. A reachability pass starts with tier 1, repeatedly admits buildable buildings and researchable ordinary technologies, then checks each next-era advancement. This rejects later-era dependencies that lock their own advancement and cycles involving a research producer's building unlocks. The pass validates content progression independently of map stock, geometry or authored sandbox spawns. Authored unit/building spawns bypass era/technology unlock gates while retaining identity, geometry and faction validation.

`ResearchCommand(playerId, buildingId, technologyId)` and `World.ValidateResearch(command)` share validation. The producer must exist, be completed, belong to the issuer and match the technology's `ResearchBuildingId`. Required technologies must already be completed by that player; each `RequiredBuildingIds` entry needs an actual completed owned building of that definition. Ordinary technology era requirements are minimum tiers. An era advancement requires exactly the immediately preceding current tier. Completed technologies cannot be researched again, and a player cannot research the same technology twice concurrently or run two era advancements concurrently.

Each building has at most one `ActiveResearch`. Research rejects a nonempty training queue, and training rejects an active research task. Different technologies may run at different buildings. Acceptance deducts the complete four-resource cost once and records pending technology identity; validation alone does neither. Accepted research continues if another prerequisite building is later destroyed. Destroying the research producer clears its active research and the player's pending identity/era flag, loses paid cost and elapsed progress, and permits a new attempt at full cost. Completed technologies and era progression persist after producer destruction. There is no player cancellation/refund command in this phase.

Unit and building definitions may declare `RequiredEraId` and `RequiredTechnologyIds`. `TrainCommand` checks unit prerequisites, and new building placement checks building prerequisites before spending or replacing builder orders. `World.ValidateRequirements(playerId, requiredEraId, requiredTechnologyIds)` gives the HUD the same read-only checks. Requirement feedback uses content display names, falling back to IDs when a display name is absent.

`TechnologyEffectKind` supports `AttackDamage = 0`, `Armor = 1` and `GatherAmount = 2`. Each effect adds its amount once to a matching owned unit when any target tag overlaps; matching multiple flags does not multiply the effect. Completed effects are recomputed from base definitions into per-player, per-unit-definition caches at completion. Existing owned units receive that cache, and future units receive it on spawn. No shared definition is mutated, enemy stats do not change, and there are no building-armor, movement or maximum-health effects in this slice. Harvesting uses effective gather amount within existing cargo-capacity and remaining-node bounds. Combat applies effective damage before the existing highest matching counter multiplier and armor. Flying projectiles retain the final damage captured at launch, including the armor calculation made then; later upgrades do not rewrite it.

Presentation reads `PlayerState.EraId`, `EraTier`, the read-only `CompletedTechnologyIds`, `HasTechnology(id)`, `BuildingState.ActiveResearch` and its `TechnologyId`, `RemainingTicks` and `TotalTicks`. Units expose current `AttackDamage`, `Armor` and `GatherAmount`. UI selection, research-panel display and progress rendering remain presentation state; only validated simulation commands spend resources or schedule research. Per-tick combat and harvesting read cached effective stats rather than scanning technologies.

## Phase 6 faction contract

`GameDefinition.Factions` contains validated `FactionDefinition` entries. `MapDefinition.PlayerFactions` contains `PlayerFactionDefinition { PlayerId, FactionId }` assignments, copied into the catalog and get-only `PlayerState.FactionId` during world creation. Later map assignment edits cannot change an existing player. Missing/null assignment arrays leave players neutral; missing/null faction arrays preserve legacy fixtures. Configured kinds are Aven Compact and Serevin March, with unique IDs and no duplicate kinds. Explicit assignments also create players with no authored entities.

Unit, building and technology definitions may require `RequiredFactionId`. Training, new placement and research reject a mismatched or neutral player before payment. Unlike era/technology setup gates, **authored faction-specific unit and building spawns also require a matching assignment**. Shared definitions remain available to both factions and neutral players. The common Storeyard can declare `CanCharter` without becoming faction-locked; only an Aven owner can use its charter action. No command changes a player's faction.

`FactionCatalog` validates assignment/definition references, supported action roles, nonnegative costs/bonuses, positive bounded timers/radii and effective carry/speed arithmetic. Mechanic technology IDs must name technologies requiring their own faction. In addition to the global technology closure, each configured faction and the neutral context gets its own progression closure, preventing a reachable-looking chain from borrowing another faction's producer or prerequisites. This checks content reachability, not map access, resource sufficiency, strategic balance or full-match viability. Effective unit totals use wide intermediate arithmetic; shared definitions are not mutated.

| Command | Authoritative behavior |
| --- | --- |
| `SetCharterCommand(playerId, buildingId, charter)` | Pay once, suspend old influence, then finish one Logistics or Muster charter |
| `DeployThreadkeeperCommand(playerId, unitId, storeyardId)` | Establish a temporary immobile relay bound to one owned active yard |
| `PackOutpostCommand(playerId, buildingId)` | Disable utility immediately and begin vulnerable timed packing |
| `DeployOutpostCommand(playerId, unitId, position)` | Begin stationary deployment at an adjacent legal footprint, rechecked at completion |
| `RepositionCommand(playerId, unitIds)` | Atomically activate eligible owned Ashrunners' movement burst and attack suppression |

`World.ValidateFactionAction` and `ValidateFactionRequirement` expose read-only feedback checks. Runtime state includes effective unit `CarryCapacity`/`MoveSpeedMillimetresPerSecond`, source IDs, relay/reposition active and cooldown timers, building active/pending charter, production work rate, and relocation state. `RelocationStage` is None, Packing, Packed or Deploying. Presentation owns markers, selected-unit details and command controls; it must replace the view when an ID changes entity kind or definition.

An Aven worker receives +2 passive carry capacity. A completed owned Storeyard's charter costs 40 Wood/20 Metal and takes 100 ticks to initialize or switch. Invalid, duplicate-active and busy orders do not charge or restart work. A switch has no active charter until completion, but its ordinary drop-off remains available. Charter changes require empty production/research; new training/research rejects while the charter changes. Logistics adds +4 local carry; Muster adds +200 permille local training work. Coverage is center-to-center, including the boundary, at 6 m by default. Matching overlapping sources never add together; the lowest yard ID identifies the chosen source. Muster advances only the front training entry using an integer remainder, so 160 work ticks take 134 uninterrupted simulation ticks at 1200 permille. It changes neither research nor construction.

Effective carry may decrease when a worker leaves coverage, a charter changes or a source dies. Already-carried cargo is never truncated: an over-capacity worker returns the existing load, and harvesting checks capacity before calculating remaining space. Resources still move through finite node stock, physical cargo and an operational owned drop-off. No charter or relay creates inventory or grants population capacity.

A Threadkeeper must deploy within an owned, completed, actively chartered yard's radius. Deployment immediately halts it for 300 ticks; Move and Stop both reject during this commitment. It relays that yard's charter for 4 m around its own position, creating no drop-off and no relay chains. Benefit requires an active source and a valid yard-to-unit tether. Switching the yard suppresses benefit while the timer continues; restored active influence can resume through a still-valid relay. Destroying the yard ends deployment and starts the full 400-tick cooldown on that tick; ordinary expiry also starts this cooldown, which decrements on following ticks. Threadkeepers and packed outposts remain unarmed even if a custom generic technology would otherwise add matching attack damage.

Reciprocal Stores adds 2 m to yard radius and tether range after its research completes, leaving relay radius at 4 m. Prepared Encampments subtracts 40 ticks from both 100-tick pack and deploy transitions. Each transition captures its duration in `RelocationTotalTicks` when its command is accepted; later research changes neither the countdown nor the progress-bar denominator of an already-running action. `RelocationRemainingTicks` counts down independently. Cancellation and the newly converted state reset the total to zero. Configuration requires the reduction to be smaller than each base duration, retaining a positive exposure window. These faction-specific benefits reference ordinary paid technologies; normal tag-scoped technology effects can coexist on those definitions.

The Supply Outpost's `IsOperational` becomes false at packing acceptance. Workers targeting it retry other eligible drop-offs; it cannot accept deposits, training or research while relocating. Packing rejects incomplete sites, queued training, active research or charter changes. Completion removes the stationary footprint and converts the same entity ID into its configured transport at the same center. Both forms must share maximum health; exact current health survives conversion and subsequent redeployment. The transport is unarmed, nonworker, not directly trainable, and costs zero population; relocatable structures may not grant population capacity. Thus conversion changes no population/reservations, increments no `DeathCount`, and charges or refunds no resources. Destruction in either form loses the paid asset once; it cannot finish a transition after death.

The cart travels through ordinary collision-safe movement. Deployment requires it to be stopped beside a grid-aligned legal footprint, with the same half-cell interaction distance used by workers. The full footprint must avoid terrain, active resource nodes, buildings and every unit circle; exact tangency is legal. Acceptance reserves **no static footprint** and charges no second building cost. The cart remains immobile and vulnerable while the timer runs. Completion rechecks geometry using direct circle/rectangle checks, avoiding a full navigation clone for each blocked retry. At zero remaining ticks, new obstruction makes it wait until the footprint is clear. Stop cancels deployment progress and returns to Packed, after which Move is legal again. Successful deployment restores the completed building under the same ID at the adjacent site, adds its footprint and replans routes. No command permits remote placement or terrain bypass.

Serevin cavalry receives +50 permille movement speed. Ashrunner reposition adds +500 permille for 60 ticks; the modifiers add, so a 5000 mm/s base becomes 5250 normally and 7750 during the burst. Activation cancels combat; explicit attacks and automatic attacks remain suppressed for the full active window. Ordinary Move/Stop and collision/incoming damage continue. The 300-tick cooldown starts at active expiry. Stop retains hold-fire after expiry, while normal movement orders retain their usual post-arrival acquisition policy. Spear counter tags still apply; neither burst nor transport grants invulnerability.

Faction influence lists and timer iteration buffers are reused. Neutral worlds skip influence traversal. Technology attack/armor/gather effects remain completion-time caches; local carry and speed derive from current positions and active states at the documented boundaries. Influence currently scans live yards/relays and their supported targets; deployment checks scan footprint cells and live bodies. These are implementation choices, not a measured faction workload or mobile performance guarantee. Housing capacity remains governed by the existing construction/death rules. The [faction bible](../design/FACTION_BIBLE.md) owns authored values and strategic limits.
